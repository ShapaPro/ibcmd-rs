# The user-facing 0.4 flow on a БСП 8.3.27 clone: import, apply, native export (#343)

`ibcmd infobase config import`, then `ibcmd infobase config apply`, then the platform's own
`config export`, `source-diff` against the edited tree. Run on 2026-09-29 with
`scripts/dropin-e2e/run_e2e.ps1` (the lab kit: `F:\ibcmd\lab\04\dropin-apply`, raw logs under `e2e\`).

## What was run

* **Corpus**: `bsp_native_20260923.bak` (БСП 8.3.27, 9 847 rows in `Config`, among them the 5 rows of an
  earlier online update: `DynamicallyUpdated`, `versions_dynupdate_*`, and the `_dynupdate_` copies of the
  common module `_ДемоЗаметки` and of a common form). Platform 8.3.27.2214, SQL Server on localhost.
* **Tree**: the platform's export of that configuration (`.../ibcmd_rs_bsp_8327_native_..._export_recheck_2/native`,
  12 198 files), copied; **25 files edited** ([`e2e-edits.json`](e2e-edits.json), 441 bytes added in all), the
  kinds patch mode carries (module texts, form bodies, templates, help; no descriptor is touched, #388):

| Edit | Files |

* **Ours**: the `iter` build without default features of feat/0.4 (`cargo build --locked --profile iter
  --no-default-features`), copied as `ibcmd.exe`, run with no folder holding `sqlcmd.exe` or `bcp.exe` on
  `PATH` (the built-in SQL client alone, as in `scripts/empty-load/run_dropin_import.ps1 -NoSqlTools`):

```
ibcmd.exe infobase config import --dbms=MSSQLServer --db-server=localhost --db-name=<clone> --data=<dir> --user=Администратор --report=<file> <edited tree>
ibcmd.exe infobase config apply  --dbms=MSSQLServer --db-server=localhost --db-name=<clone> --data=<dir> --user=Администратор --force --dynamic=disable --report=<file>
```

* **Check**: the platform's `ibcmd infobase config export ... --threads=8 <dir>` of the clone, then
  `ibcmd-rs source-diff -o <json> <edited tree> <export>`; `ConfigDumpInfo.xml` compared with every
  `configVersion` blanked (the platform stamps new version hashes).

## Findings

1. **The platform's whole-tree import cannot be the comparator.** It refuses this configuration's own export
   on this build, deterministically. `import files --partial` works and is the comparator used above.
2. **Patch mode restages the whole tree with fresh versions.** 9 514 of 9 835 `configVersion` values of the
   export differ from the input's `ConfigDumpInfo.xml` after our import and apply (and after the platform's
   apply of our stage); after the platform's partial flow 42 differ. Everything that reads versions or change
   registrations sees the whole configuration as changed: an incremental export against the old
   `ConfigDumpInfo.xml`, and the exchange plans (the apply resets the message numbers of ~4 700 objects). It
   is the "delta stage" of the import track (#388, `docs/import/patch-mode.md` section 8.1).
3. **The recovery artifact of the apply is large for such a stage**: 9 176 files, 78 MB in
   `%TEMP%\ibcmd-rs\config-apply-recovery\<db>-<token>` (14 s of the 62 s), never cleaned. A delta stage would
   shrink it to the changed rows; `--recovery-blobs none` (a hash manifest only) exists in the apply's own
   command line and not in the drop-in's.
4. **The online-update rows of the corpus went through**: the stage carries the tree's text for the two
   objects with `_dynupdate_` rows, the apply folded the alias rows, the export has the edited text.
5. **Load matters**: see the table; the apply's inventory and fingerprint queries and the recovery
   artifact grow the most.
