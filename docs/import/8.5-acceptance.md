# Platform 8.5 import acceptance (#419)

Measured on 2026-10-01 with native platform 8.5.1.1150, SQL Server `localhost`,
Windows authentication, and disposable import-track databases only. The candidate
was built from `29a636e655684854162b36bb83cdca16e55f8442` (the integration branch
through `9d1d6158`, plus the patch-stage root-family change `d9a3e3bd`). Binary
SHA-256: `24a29506f8fc88b9145e9b60c1dfab564dad696e38a1a9ea94648c21283439ed`.

All own imports use the drop-in `infobase config import` with its default flags;
there is no `--no-verify`, forced `--base-free`, or `--per-row` bypass. SQL reports
are the importer's own JSON. Apply/export are the native utilities. Each native
write holds the FIFO native lock for that single command.

## Empty native infobase

`run_empty85_acceptance.ps1` first creates an empty SQL database with the lab
helper, then creates the infobase with native 8.5 (`--locale=ru_RU`). Import of
the unedited native BSP 8.5 export automatically selects base-free mode.

| Step | Result |
|---|---|
| Native infobase create | exit 0, 4.3 s |
| Default own import | exit 0, 20.2 s, 9,948 staged rows |
| Stage verification | 12,336 checked and identical files |
| Native apply | exit 0, 60.7 s |
| Native export | exit 0, 14.3 s |
| Source/export comparison | 12,336 exact files; no missing/extra files |
| `ConfigDumpInfo.xml` | exact after replacing **only** `configVersion` attribute values |

Evidence: [empty85.json](evidence/419/empty85.json). The empty infobase has no
users, so its native commands omit `--user`; this avoids borrowing the corpus
administrator identity for a newly created database.

## A real palette-color patch

The unedited native tree was copied into the import lab, and precisely
`PaletteColors/ВниманиеБИПЦветФона.xml` changed from `<Color>#FFEC9D</Color>` to
`<Color>#FFEC9E</Color>`. The default patch stage compiled that one descriptor,
staged five rows and verified all 12,336 files. Native apply (41.6 s) and export
(12.6 s) exited 0. All configuration files matched the edited tree exactly,
including `ConfigDumpInfo.xml` after replacing only its `configVersion` values.

Evidence: [palette85.json](evidence/419/palette85.json). This accepts the
patch-stage change to consume the same root-family table as the source scanner,
including `PaletteColors` and `ExternalDataSources`; `CommonModules` retain
their separate stage path.

## Add/remove fixtures and the independent service inventory

The existing `b85add`/`b85rem` fixtures edit descriptors and bodies but leave their
original `ConfigDumpInfo.xml` unchanged. Thus comparing their complete export
to that original file, even after ignoring generation hashes, must fail:
the added or removed metadata entries are real inventory differences. The
strict harness now records this and refuses to silently skip the entire file.

The own cycles nevertheless passed import verification and native apply/export:

| Fixture | Default own stage | Native apply/export | Files against edited tree |
|---|---|---|---|
| `b85add` | 2 new objects, 4 compiled descriptors, 11 staged rows; guard 12,339/12,339 | exit 0, 49.5/16.3 s | 12,339 exact, plus stale fixture dump-info |
| `b85rem` | 2 compiled descriptors, 5 removed rows and deleted names, 22 staged rows; guard 12,329/12,329 | exit 0, 50.0/17.3 s | 12,329 exact, plus stale fixture dump-info |

Original comparisons are preserved in
[add85-fixture-comparison.json](evidence/419/add85-fixture-comparison.json) and
[rem85-fixture-comparison.json](evidence/419/rem85-fixture-comparison.json).

The independent native reference uses fresh BSP 8.5 clones and native
`config import files --partial` of the fixture's touched files, followed by
native apply and full export. It does not use this program to create its stage.
The complete own and native exports are then compared, with **only**
`configVersion` values ignored in dump-info. This matches the native reference
method used by the restructuring lab.

The add fixture's independent native cycle exited 0 (import 61.1 s, apply
59.8 s, export 12.5 s). All 12,339 files matched the own result and dump-info
was identical after normalizing only `configVersion`:
[add85-vs-native.json](evidence/419/add85-vs-native.json).

Native partial import of the original removal descriptors alone refused
`Catalog.Заметки` as protected vendor metadata. The rejected stage had zero
rows and was not applied; [the refusal report](evidence/419/native-partial-rem-refusal.json)
is retained. A second regression removes the non-default
`Catalog._ДемоКонтрагенты.Form.ДокументыКонтрагентов` and the demo picture
template `DataProcessor._ДемоШаблонСообщенияДляЗаказаПокупателя.Template.Логотип`.
These edit functions are `formdel_demo,tpldel_demo` in the lab kit.

The own demo removal compiled two descriptors, removed four rows, staged seven
rows and verified 12,331/12,331 files (13.3 s import, 30.6 s native apply,
12.8 s native export). The independent native reference includes
`Configuration.xml` as well as the edited surviving owner descriptors. Without
the root, native partial import also refused the demo owner. Including it uses
the same native partial-import scope as the successful add reference, and
retains vendor support throughout. Native import/apply/export exited 0
(49.9/45.9/11.7 s). All 12,331 configuration files matched the own export;
dump-info's names, ids, hierarchy and bytes also matched after blanking only
`configVersion`. Evidence:
[remdemo85-vs-native.json](evidence/419/remdemo85-vs-native.json) and
[touched files](evidence/419/remdemo85-touched.json).

An exploratory native reference with support disabled was measured separately
in the lab (`out/native-reference-rem85nativeeditable.json`). It is **not** an
acceptance oracle: its support state differs from the own cycle. No support
artifact/inventory exclusions are used in either accepted twin comparison.

A native full import of the entire add fixture was attempted first, but native
8.5 refused unrelated unchanged references to
`ChartOfCharacteristicTypes.ОбъектыАдресацииЗадач.ВсеОбъектыАдресации`.
[The native error](evidence/419/native-full-import-refusal.txt) is preserved;
that failed stage was not applied or reused. The partial reference includes
every edited surviving file, including the new form and configuration root.
The guarded reuse option applies only to rejected clones with zero ConfigSave
rows; no pending native stage is overwritten.

## Regression coverage and reproducibility

The guard tests exercise equal, changed, missing and extra files under
`PaletteColors`, `Bots`, `IntegrationServices` and `ExternalDataSources`; the
patch-stage test checks every model root family and the special module path.
These synthetic tests prove classification/refusal behavior for kinds absent
from this BSP corpus, rather than claiming unmeasured database acceptance.

[Quick gates](evidence/419/quick-gates.txt) passed formatting, physical-adapter
policy, workspace clippy and 3,575 root library tests (9 ignored). The bounded
`test_native_lock.ps1` mock tests both heavy/no-heavy paths, success and throwing
bodies, exactly-once execution and release order. They caught and prevent the
PowerShell dynamic-scope recursion in the old native-lock wrapper.

The scripts live in `scripts/import-lab/`. Reports and logs live in
`F:\ibcmd\lab\04\import\out` and `logs`. `compare_dump_info.py` normalizes only
`configVersion="..."`; it preserves metadata names, ids, hierarchy, formatting
and every other byte. `run_override_acceptance.ps1 -DumpInfoReference` permits
an independently produced native reference for intentionally edited fixtures.
